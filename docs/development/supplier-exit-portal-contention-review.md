# 退出审批与门户并发、历史补偿边界

2026-10-22。本段只增加真实事务回归和历史处理设计，不增加生产补偿入口，不修改旧退出或封存记录。

## 可单独验收的并发目标

`PortalAuthIT` 新增两项用例，各自分别执行登录、邀请注册，共四种争用场景。使用隔离 MySQL 的两个业务线程及独立事务：审批完成全部实际写入后，由测试外层事务暂缓提交；门户请求必须在 InnoDB `data_lock_waits` 中出现供应商行锁等待，再释放审批事务。没有模拟认证、注册、回收或审计服务，没有在生产代码增加等待逻辑。

- 审批提交：等待中的登录与注册均拒绝，账号、会话总数不增加，旧会话已撤销，有效邀请已撤销，供应商为 EXITED。
- 审批回滚：等待中的登录与注册仍因 SUBMITTED 退出申请被拒绝，不新增账号或会话，不永久撤销原会话。申请人正式撤回后，旧会话可继续使用，登录或原邀请注册成功。
- `finally` 释放测试闩锁并关闭线程池，等待有超时；数据库锁观测使用临时容器 root，仅测试可用，不授予生产账号监控权限。

覆盖的是“退出审批持锁先行”的提交/回滚竞态，不是所有锁序穷举，也不代表注册先行、租户停用、密码维护等全部并发已验收。这里验证实际锁等待，避免仅靠启动闩锁或请求先后冒充并发证据。

## 历史已退出主体：只读识别，不自动补偿

新审批会回收本地门户账号；既有 BUSINESS_CLOSED 记录不能重新审批、补写历史事件或重新计算原封存摘要。缺少 `LOCAL_PORTAL_RECOVERY` 仅说明没有此版本联动证据，不直接等于存在可访问漏洞；实时 EXITED 门禁仍会拒绝门户访问。需要区分存量凭证未永久撤销与实际可访问性。

后续只读核查需显式租户、供应商/申请范围、分页和只读权限：先检查申请与供应商当前状态、封存完整性，再分别统计账号状态/版本、未撤销会话（另列未过期数）、有效未消费邀请，以及是否已有回收事件和逐账号审计。不输出密码哈希、令牌哈希、邀请凭证或联系方式，不把外部目录当成本地账户。核查中发现重建合作关系、状态不一致、摘要不一致或重复退出历史，应列为人工确认项，不直接批量处理。

若要上线历史补偿，必须作为独立业务功能实现并验收：

1. 新增独立权限、双人复核、明确原因和证据；Console 不得凭跨租户入口绕过授权。
2. 预览记录范围、数量、版本和摘要；执行时重新锁定供应商，确认仍为 EXITED、目标申请有效、无重新合作，重新读取账号/邀请，预览失效必须拒绝。
3. 独立补偿单与幂等键；账号版本提升、会话及邀请撤销、新补偿审计同事务，失败全回滚。重复执行不重复增加版本，不伪造原退出审批人。
4. 保持原申请、事件及封存摘要不变；新补偿记录单独关联旧申请，明确处理时间与操作者，不能把后来处理冒充当时已完成。
5. 外部核查继续 NOT_VERIFIED；只有真实厂商回执或既定人工证据流程才能更新相应结果。

本轮未读取或改写本地旧库，未执行 repair、清库、关闭校验或历史补偿。上述补偿功能仍未实现，不计为交付完成。
