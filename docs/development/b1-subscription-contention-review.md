# B1 订阅分配、取消争用与审计故障验收

## 双连接争用

隔离 MySQL 中使用两个工作线程、独立数据库事务及不同 `CONNECTION_ID()`。第一事务完成变更后保持未提交，通过屏障让第二事务进入操作；第二调用在第一释放前不能完成。释放后检查两侧结果与最终记录，不使用串行请求替代争用测试。

| 场景 | 预期 |
|---|---|
| 分配先持锁，旧版本取消随后进入 | 新计划提交；取消得到版本冲突；旧计划已替换，新计划不能被旧请求取消 |
| 取消先持锁，分配随后进入 | 原计划取消并审计一次；随后正常分配新计划；两个操作各递增一次租户版本 |
| 两个取消使用同一列表版本 | 首个成功，另一个冲突；版本只递增一次，审计只有一条，无重复取消 |

全部场景同时检查当前有效套餐不变、待生效计划数量正确、新计划 ID 不等于旧计划，线程池及屏障在 finally 中释放。测试用 200ms 的未完成断言配合写入屏障及连接 ID，不声称检查了数据库引擎内部锁等待表，也不等于分布式部署压测。

## 审计失败回滚

只在 Testcontainers 隔离库使用容器内管理员创建触发器，对指定测试计划的 `SUBSCRIPTION_CANCEL` 审计插入抛错；不影响其它对象。应用账号仍使用原权限，不授予 SUPER、不修改 binary log 或信任配置。经过真实 Console 登录、授权和幂等接口请求取消，预期 500。检查订阅仍待生效、取消时间未写入、租户版本未变化且无审计记录。

finally 删除该测试触发器后，用完全相同的请求和幂等键重试成功，再重复请求只返回同一结果、只留一条审计。这同时验证失败请求未留下阻断重试的幂等占位。未修改本地旧库、未 repair 或关闭 Flyway 校验。
